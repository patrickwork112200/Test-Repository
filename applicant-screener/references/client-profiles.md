# Client Profiles

Per-client memory so each screen starts from what earlier screens learned,
instead of re-deriving the client from scratch. Step 1 reads the matching
entry when the client is identifiable from the JD; Step 4 takes the TCV
duration default from it; Step 7 appends (dated) anything new the screen
surfaced — panel feedback, rejection reasons, logistics.

**The one hard rule:** a stored profile *seeds* weights, probes, and rate
defaults. It never overrides evidence in the current materials, and it never
substitutes for feedback tied to the requisition actually being screened.
When a stored note and the current JD/panel feedback disagree, the current
requisition wins — and note the disagreement so the profile can be updated.

Maintenance: append under the client's headings with a date stamp
(`2026-07-24 — panels asked live SQL on screen-share`). Prune entries the
user says are stale. If a screen involves a client not listed here, add a
new entry in the same shape.
